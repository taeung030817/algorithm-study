
# Binary Search (이진 탐색)

## 개념

정렬된 데이터에서 값을 찾을 때, 매번 중간값과 비교해서 절반의 가능성을 버리는 탐색 방법이다.

예를 들어 1~1000 사이의 숫자를 맞추는 게임을 생각해보자. 상대가 마음속으로 숫자 하나를 정하면, 나는 매번 "중간값"을 불러서 그보다 큰지 작은지만 알아낸다. 한 번 물어볼 때마다 남은 가능성이 절반으로 줄어든다.

- 1~1,000: 최대 10번이면 맞출 수 있다
- 1~1,000,000: 최대 20번
- 1~1,000,000,000: 최대 30번

데이터가 1,000배씩 커져도 필요한 비교 횟수는 겨우 10번씩만 늘어난다. 이게 이진 탐색의 핵심이다.

## Linear Search와 비교

- **Linear Search**: 첫 번째 항목부터 마지막 항목까지 순서대로 확인. 데이터가 백만 개면 최악의 경우 백만 번 비교해야 할 수도 있다.
- **Binary Search**: 정렬된 데이터라면 비교할 때마다 절반을 버리기 때문에, 데이터가 아무리 커져도 필요한 비교 횟수는 로그 단위로만 늘어난다.

데이터 크기가 커질수록 두 방식의 격차는 극단적으로 벌어진다. 어느 시점부터는 "빠르다"는 정도를 넘어서, 데이터 크기 자체가 더 이상 문제가 되지 않는다.

## 시간복잡도

Binary Search의 시간복잡도는 **O(log₂n)** 이다.

## 전제조건

**데이터가 정렬되어 있어야 한다.** 정렬되지 않은 데이터에 이진 탐색을 적용하면 탐색이 실패하거나 잘못된 결과를 반환할 수 있다. 그래서 실무에서는 탐색 자체보다 "누가, 언제 정렬을 해두는가"가 더 중요한 문제가 되는 경우가 많다.

## 실전 활용 사례

### 데이터베이스 인덱스

DB 인덱스 내부에서는 이진 탐색(또는 이를 응용한 트리 구조)이 동작하고 있다. 정렬된 인덱스 구조 덕분에 수백만 건의 데이터에서도 빠르게 값을 찾을 수 있다.

### Git bisect

`git bisect`는 어떤 커밋이 빌드/코드를 망가뜨렸는지 찾을 때 이진 탐색을 사용하는 git 명령어다.

예를 들어 500번째 커밋에서 에러가 발생하고, 그 이전 커밋들에서도 에러가 있었을 가능성이 있다면, 매번 중간 지점의 커밋으로 체크아웃해서 정상/비정상 여부를 확인한다. 이렇게 범위를 절반씩 좁혀가며 문제가 시작된 커밋을 빠르게 찾아낸다.

- commit: git에서 코드 변경사항을 저장하는 단위
